# 量子回路シミュレーション・性能評価ツール (quantum-sim-bench)

> **重要: 実行はすべて CPU(NumPy)です。GPU は使用していません。** GPU・Docker・Slurm・複数ノード・クラウドは未実装または未検証です(「現在の到達点」「既知の制約」参照)。

## 1. このプロジェクトでできること

量子コンピュータの計算を、通常のコンピュータ(CPU)上でシミュレーションするアプリです。量子回路を実行して計算結果を確認したり、回路の規模や並列実行の条件を変えて、計算時間やメモリ使用量がどう変化するかを調べたりできます。

- **回路を試す**: GHZ 状態 / 量子フーリエ変換(QFT) / ランダム回路を計算し、測定確率・複素振幅・実行時間を表示
- **規模とコストを知る**: 量子ビット数 n に対する理論メモリ(16×2ⁿ バイト)を、実行せずに確認
- **性能を測る**: 時間・メモリ・ばらつき(変動係数)を、参照結果との一致確認つきで測定。CSV 出力
- **並列実行の実測例を見る**: ワーカー数 × スレッド数 を独立に変えた本測定の結果を、解釈の限界つきで表示
- **数式と用語を学ぶ**: 状態ベクトル・GHZ・QFT・ベンチマーク指標の解説(具体例の数値は実際の計算結果)

## 3. 量子シミュレーションの仕組み

状態ベクトル方式では、n 個の量子ビットの状態を、2ⁿ 個の複素振幅 α_x で表します。

$$|\psi\rangle=\sum_{x=0}^{2^n-1}\alpha_x|x\rangle,\qquad P(x)=|\alpha_x|^2,\qquad \sum_x|\alpha_x|^2=1$$

- 実装は、長さ 2ⁿ の `complex128` 配列(`src/qsimbench/statevector.py`)。量子ビット 0 番が、インデックスの最上位ビット(ビット列の左端)
- ゲートは `tensordot` で該当する軸に作用させて更新。確率は絶対値の 2 乗
- **メモリ**: 振幅数 $2^n$、状態ベクトル本体の理論メモリ $M\approx16\times2^n$ バイト(例: n=20 で 16 MiB、n=30 で 16 GiB)。**状態ベクトル本体のみの理論値**で、計算中のピークは一時配列などのため大きくなります(本測定では約 3 倍)。状態ベクトル方式に限った式です
- **GHZ 状態**: $|\mathrm{GHZ}_n\rangle=(|0\rangle^{\otimes n}+|1\rangle^{\otimes n})/\sqrt2$。測定すると全 0 か全 1 が確率 1/2 ずつ
- **QFT**: $|x\rangle\mapsto\frac1{\sqrt N}\sum_{y}e^{2\pi i xy/N}|y\rangle$($N=2^n$)。出力は $\sqrt N\cdot$`numpy.fft.ifft`(符号の規約が e^{+i…})と一致。上の式との一致は自動テストで確認済み(`tests/test_explain.py`)

詳しい解説(記号の意味・具体例・コードとの対応)は、アプリの「⑤ 数式としくみ」にあります。

## 4. ベンチマークと並列実行の仕組み

- **ベンチマーク**: 同じ条件で複数回測り、平均・中央値・最小・最大・標準偏差・変動係数(CV = 標準偏差 ÷ 平均)で評価。ウォームアップ回は捨てる。時間は `perf_counter`、メモリは別実行で `tracemalloc`(Python/NumPy の確保量のピーク。OS 全体の使用量ではない)
- **ワーカー数**: 独立したジョブを同時に動かす数(スループットを上げる設定)。**スレッド数**: 1 ジョブ内で BLAS が計算を分担する数
- 並列にしても、CPU・メモリ帯域・キャッシュは共有されるため、**1 ジョブあたりの時間は伸びることがあり、必ず速くなるとは限りません**。壁時計時間(バッチ全体)と、ジョブ内の計算時間は別の量です
- 各ジョブのスレッド数は `threadpoolctl` で設定し、実際に適用された値を検出して記録(`job.json` の `thread_info`)

## 5. 実測結果とその解釈

QFT n=16,18、各条件 4 ジョブ × 3 ラウンド、条件の順序は seed 付きでシャッフル(`docs/measurements/`、元データ `sweeps/` と同一)。i7-8550U(4 コア/8 スレッド)のノート PC、他アプリ起動中、CPU のみ。

| ワーカー | スレッド | 壁時計 中央値 [s](最小〜最大) | 1 ジョブの回路時間 n=18 [s] |
|---:|---:|---|---:|
| 1 | 1 | 34.1 (34.1〜37.7) | 0.99 |
| 1 | 2 | 33.7 (32.9〜38.9) | 0.93 |
| 1 | 4 | 33.5 (31.1〜34.4) | 0.88 |
| 2 | 1 | 21.1 (20.9〜22.0) | 1.23 |
| 2 | 2 | 21.5 (21.4〜27.4) | 1.22 |
| 2 | 4 | 24.0 (22.5〜38.1) | 1.40 |
| 4 | 1 | 16.4 (16.1〜17.4) | 2.04 |
| 4 | 2 | 16.6 (16.5〜19.1) | 1.94 |

(ワーカー 4 × スレッド 4 は、論理コア数 8 を超えるためスキップしました。これは今回の測定における保守的な制限で、超過が常に遅いという意味ではありません。回路時間は、ラウンドごとの中央値の中央値です。)

**言えること**: この PC・この負荷では、ワーカーを増やすと壁時計時間は短くなった(1→2 で約 1.6 倍速、1→4 で約 2.1 倍速)が、1 ジョブあたりの回路時間は伸びた。スレッド設定は全 96 ジョブで要求どおり適用されたことを確認した。

**言えないこと**: スレッド数の効果(範囲が重なり、差を断定できない)。伸びの原因(メモリ帯域・ハイパースレッディング・CPU 周波数などの切り分けはしていない)。最適な設定(1 台・1 種類の負荷・3 ラウンドで、外れ値も含む)。他の PC・GPU・クラスタへの一般化。

## 9. 用語集

アプリの「⑥ 用語集」に、詳しい説明つきで同じ内容があります。

<!-- GLOSSARY:START -->
- **量子ビット（qubit）** — 量子計算の最小単位。普通のビットが 0 か 1 のどちらかなのに対し、0 と 1 の「重ね合わせ」を取れる。
- **量子状態** — 量子ビットの「いまの状態」。このアプリでは、複素数の並び(状態ベクトル)で表す。
- **重ね合わせ** — 「0 でもあり 1 でもある」ように、複数の状態が振幅という重みつきで同時に含まれていること。
- **複素振幅** — 各ビット列に対応する複素数。大きさの 2 乗が測定確率、角度(位相)は干渉に効く。
- **測定確率** — 測定したときに、あるビット列が得られる確率。振幅 α に対して |α|²。
- **量子ゲート** — 量子状態を変える操作。数学的には、状態ベクトルにかける行列(ユニタリ行列)。
- **量子回路** — 量子ゲートを順番に並べた計算の手順。
- **GHZ状態** — 全部 0 の状態と全部 1 の状態の重ね合わせ。測定すると全 0 か全 1 のどちらかだけが半々で得られる。
- **QFT** — 量子フーリエ変換。古典の離散フーリエ変換に対応する量子回路。
- **状態ベクトルシミュレーション** — 量子状態の全ての振幅(2ⁿ 個)をメモリに持ち、ゲートごとに更新して計算するシミュレーション方式。
- **ベンチマーク** — 決まった条件でプログラムを実行して、性能(時間・メモリなど)を測り、比較すること。
- **ワーカー** — 独立したジョブ(実験)を同時に実行するプロセスの数。
- **スレッド** — 1 つのプロセスの中で、計算を分担して並列に進める仕組み。ここでは BLAS(行列演算ライブラリ)の並列数。
- **並列実行** — 複数の処理を同時に進めること。ワーカー(ジョブ間)とスレッド(ジョブ内)の 2 つの階層がある。
- **メモリ使用量** — プログラムが使うメモリの量。理論値と実測値は別物。
- **参照結果** — シミュレータの計算が正しいかを確かめるための、別の方法で求めた正解。
- **数値誤差** — コンピュータの有限桁の計算で生じる、真の値とのわずかなずれ。
- **変動係数（CV）** — ばらつきの大きさを平均に対する割合で表した値。標準偏差 ÷ 平均。
- **基底状態・ビット列** — 「000」「101」のような、0 と 1 の並びで決まる状態。n 量子ビットなら 2ⁿ 通りある。
- **位相** — 複素振幅の角度。確率(大きさ)には現れないが、ゲートを重ねたときの強め合い・打ち消し合いを決める。
- **正規化** — 全てのビット列の確率を足すと 1 になること(Σ|α|²=1)。
- **干渉** — 複素振幅が足し合わされるとき、位相がそろえば強め合い、逆なら打ち消し合う現象。
- **もつれ（エンタングルメント）** — 複数の量子ビットの状態が、1 つずつに分けて書けない関係。
- **ショット（測定回数）** — 同じ回路を何回測定するか。
- **乱数シード** — 乱数の出方を決める数。同じ値なら同じ乱数列になり、結果を再現できる。
- **代表的なゲート(H・CX・CP・SWAP・RY・RZ)** — H: 重ね合わせを作る / CX: 片方が 1 のときだけ他方を反転 / CP: 片方が 1 のとき位相を回す / SWAP: 入れ替え / RY・RZ: 回転。
- **解析解** — 式で書ける、正確な答え。
- **密行列** — 2ⁿ×2ⁿ の全要素を持つ行列。ここでは、回路全体を 1 つの行列で表したもの。
- **TVD（全変動距離）** — 2 つの確率分布の違いの大きさ。0 なら完全に一致、1 なら全く重ならない。
- **倍精度複素数** — 実部と虚部を、それぞれ 8 バイト(倍精度)で持つ複素数。合計 16 バイト。
- **KiB・MiB・GiB** — 1024 を基準にしたデータ量の単位。1 KiB=1024 バイト、1 MiB=1024 KiB、1 GiB=1024 MiB。
- **一時配列** — 計算の途中で、一時的に作られる配列。
- **理論値・実測値・推定値** — 🔵 理論値は式から、🟢 実測値は実際に測って、🟠 推定値は実測などから見積もって得る値。
- **壁時計時間（wall-clock time）** — 時計で測った、実際に経過した時間。
- **ウォームアップ** — 測定に含めない、準備のための実行。
- **オーバーヘッド** — 目的の計算以外にかかる時間や資源。
- **スループット** — 単位時間あたりに処理できる量。
- **資源競合** — 複数の処理が、CPU のコア・キャッシュ・メモリ帯域などを取り合うこと。
- **BLAS** — 行列・ベクトル演算の高速なライブラリ。NumPy は内部で OpenBLAS という実装を使う。
- **論理コア・物理コア** — 物理コアは CPU の実際の計算部品の数、論理コアは OS から見えるコアの数(ハイパースレッディングで物理の 2 倍に見えることがある)。
- **tracemalloc** — Python が確保したメモリを追跡する標準機能。
- **フーリエ変換** — 信号を、いろいろな周波数の波の足し合わせに分解する変換。

## 計測の定義(実測 / 理論 / 推定)

| 量 | 種別 | 方法 |
|---|---|---|
| 実行時間 | **実測** | `time.perf_counter`、ウォームアップ回を除外し反復回の平均・標準偏差・最小・中央値・変動係数 |
| ピークメモリ | **実測** | `tracemalloc` のピーク(時間とは別実行)。**プロセス RSS ではなく Python/NumPy 確保分のみ** |
| 状態ベクトルサイズ | **理論値** | 16·2ⁿ バイト(complex128) |
| TVD の目安 | **理論値** | 有限ショットの期待量 ≈ √(k/(2π·shots))(k=非ゼロ確率状態数) |
| 時間のべき乗フィット | **実測値へのフィット** | n ≥ 12 の log₂(時間) 対 n の傾き(外挿値ではない) |

| 16 | 0.154 | 0.0007 | 3.1 MB | 2e-17 |
| 18 | 0.594 | 0.0031 | 12.6 MB | 8e-18 |

## ジョブ管理(ローカルキュー, Phase B)

複数の実験設定を「ジョブ」として登録し、ローカル CPU 上で同時実行数に上限をつけて実行します。**Slurm 等の本物のスケジューラではなく、単一 PC 内のファイルベースの最小実装です。**

```powershell
python -m qsimbench submit configs/example_small.toml configs/example_qft.toml   # 登録(queued)
python -m qsimbench work --workers 2                                             # 実行(既定は 1 = 逐次)
python -m qsimbench list                                                         # 一覧
python -m qsimbench show <job_id>                                                # 詳細(JSON)
python -m qsimbench retry                                                        # 失敗ジョブを新ジョブとして再登録
python -m qsimbench work                                                         # 再登録分を実行
python -m qsimbench cancel <job_id>                                              # queued のみ取り消し可
python -m qsimbench export --jobs jobs.csv --results results_all.csv             # CSV(既存ファイルは上書きしない)
python -m qsimbench compare-workers configs/example_parallel.toml configs/example_parallel.toml --workers 1 2
python -m qsimbench analyze results/<run>/results.csv                            # スケーリング要約
```

保存先は `--root`(既定 `jobs/`)。既存の `python -m qsimbench run ...`(1プロセスで直接実行)はそのまま使えます。

### アーキテクチャ

```
CLI (cli.py)
 ├─ run ─────────────────────────────▶ jobs.execute()  ※直接実行(Phase 1-2)
 └─ submit/work/list/retry/... ─▶ jobqueue.py(スケジューラ)
                                    │ 子プロセスを最大 workers 個まで起動
                                    ▼
                          python -m qsimbench worker <job_dir>
                                    └▶ jobs.execute() ─▶ circuits / statevector / reference / benchmark
jobs/<job_id>/  job.json  config.toml  worker.log  worker_result.json  runs/<run_id>/{config.toml,job.json,run.log,results.csv}
```

- シミュレータ本体は変更せず、既存の `execute()` を子プロセスから呼ぶだけです。
- `job.json` を書くのはスケジューラと `cancel` のみ。ワーカーは `worker_result.json` だけを書きます。
- 各ジョブを別プロセスにするのは、(1) 1 ジョブの異常終了が他に波及しない、(2) OS 視点の資源を **ジョブ単位で** 取れる、ためです。

### ジョブ状態と遷移

```
queued ──▶ running ──▶ succeeded
   │           └─────▶ failed
   └──▶ cancelled
```

| 状態 | 意味 |
|---|---|
| queued | 登録済み・未実行(`submit` 直後) |
| running | 子プロセス実行中 |
| succeeded / failed | 終了(終了コード 0 / それ以外、またはワーカーが結果を残さず異常終了) |
| cancelled | **queued のまま取り消したもの** |

- **実行中ジョブの中断は未実装**です(running から cancelled には遷移しません)。
- 不正な遷移(例: queued → succeeded)は例外になります。
- 再実行(`retry`)は failed ジョブの設定を**新しいジョブ**として登録します(`retry_of` に元の job_id)。元のジョブ・ログ・結果は変更しません。
- `work` は、あるジョブが失敗しても残りを実行します(既定)。`--fail-fast` なら失敗後に新規起動せず、残りは queued のままです(実行中のジョブは完走させます)。
- 同時実行は `--workers`(既定 1、上限は論理コア数)。並列起動時は、各ジョブの**推定**ピークメモリ(理論状態サイズ×3)の合計が利用可能 RAM の 60% を超える場合、起動を待たせます。この推定は経験則であり保証ではありません。
- 各ジョブの BLAS スレッド数は `--threads-per-job`(既定: 物理コア数 ÷ workers)で、`OMP/OPENBLAS/MKL_NUM_THREADS` として子プロセスに渡し、`job.json` に記録します。

### 逐次実行と並列実行の違い

| | `--workers 1`(逐次) | `--workers N`(並列) |
|---|---|---|
| 壁時計時間 | 長い | 短くなりうる(CPU・メモリ帯域が空いている範囲) |
| 各ジョブの測定時間 | 他ジョブの影響なし | **他ジョブと CPU・メモリ帯域を奪い合うため伸びる** |
| 用途 | 性能評価(時間の比較) | スループット(多数ジョブの消化) |

**性能評価の数値(時間)を比較したいときは逐次実行を使ってください。** 並列実行下で測った時間は、`concurrency_at_start` が 1 より大きいジョブでは負荷の影響を含みます。

### 結果の記録とリソース計測

`jobs/<job_id>/job.json`(主な項目)

| 項目 | 意味 |
|---|---|
| `job_id`, `seq`, `retry_of` | 一意 ID、登録順、再実行元 |
| `state`, `exit_code`, `error` | 状態、終了コード、エラー(失敗時は traceback 全文) |
| `submitted_at` / `started_at` / `finished_at` | 登録・開始・終了時刻 |
| `duration_s` | **実測**。子プロセス起動から終了まで(Python 起動・import を含む) |
| `worker_run_duration_s` | **実測**。`execute()` 内の時間(起動・import を除く) |
| `workers`, `threads_per_job`, `concurrency_at_start` | 実行時の同時実行設定と、開始時点で動いていたジョブ数(自分を含む) |
| `resources.peak_rss_bytes` | **実測(OS 視点)**。そのワーカープロセス全体のピーク常駐メモリ。Windows は `peak_wset`、Linux は `ru_maxrss`。取得不可なら null |
| `resources.cpu_time_s` | **実測**。user+system の累積 CPU 秒 |
| `resources.cpu_util_cores_avg` | cpu_time_s ÷ プロセス生存時間。**平均値**であり瞬間 CPU 使用率ではない。1.0 超はマルチスレッド |
| `log_path` | `worker.log`(ワーカーの標準出力・標準エラー。クラッシュ時の情報源) |

**Python メモリ(tracemalloc)と OS 視点のメモリ(peak_rss)は別物**です。前者は結果 CSV の `peak_mem_bytes_measured`(NumPy 配列を含む Python の確保分のみ)、後者は Python 本体・NumPy・pandas の常駐分を含むため、小さい n では後者がはるかに大きくなります。

| 列 | 種別 | 意味 |
|---|---|---|
| `circuit`, `depth`, `input_value`, `seed`, `warmup`, `repeats`, `shots` | 条件 | 実験条件(depth はランダム回路のみ有効) |
| `status` | | `ok` / `failed`(失敗した点は 1 行だけ残り、`error` に最終行) |
| `qubits`, `gates` | 条件 | 量子ビット数、ゲート数 |
| `time_mean_s`, `time_std_s` | 実測 | 反復時間の平均、標本標準偏差(n-1) |
| `time_min_s`, `time_max_s`, `time_median_s` | 実測 | 最小・最大・中央値 |
| `time_sem_s` | 実測から算出 | 平均の標準誤差 std/√repeats |
| `time_cv` | 実測から算出 | 変動係数 std/mean(反復間ばらつき) |
| `times_s` | 実測 | 各反復の時間(JSON 配列) |
| `gates_per_s` | 実測から算出 | ゲート数 ÷ 平均時間 |
| `peak_mem_bytes_measured` | 実測 | tracemalloc のピーク(measure_memory=true のとき) |
| `statevector_bytes_theory` | **理論値** | 16·2ⁿ バイト |
| `max_abs_error_vs_reference`, `reference_kind` | 検証 | 参照計算との最大絶対誤差、参照の種類(analytic/dense/none) |

`results.csv` を保存する前の run_id は `日時-name-<6桁hex>` で一意です。各 run・各ジョブは新しいディレクトリに保存し、既存は上書きしません。

## 性能評価の方法と再現性

1. 条件を TOML に書く(`configs/*.toml`)。`seed` で回路(ランダム回路)とサンプリングが決まり、同じ設定・シードなら `tvd_sampling_vs_sim` など確率的な値も再現します(**実行時間は再現しません**)。
2. 逐次で実行し、`warmup` 回を捨て `repeats` 回を記録します。
3. `python -m qsimbench analyze results/<run>/results.csv` で、n ≥ 12 での log₂(時間)–n の傾き、ピークメモリ/理論値の比、最大変動係数を得ます(測定範囲内のフィットであり、外挿ではありません)。
4. 反復回数によるばらつきの確認は、`repeats` を 3, 5, 10 と変えた設定を別々に実行し、`time_cv`・`time_sem_s` を比べます(`time_sem_s` は repeats を増やすと小さくなるはずの量、`time_cv` はノイズの大きさそのもの)。

### 測定例(2026-10-28、i7-8550U 4コア/8スレッド、RAM 7.9 GiB、Python 3.11.0、他アプリ起動中)

`analyze` の結果(`example_qft.toml` の run): 傾き 1.22(n≥12、4 点)、n=20 のピーク実測/理論 = 3.00、最大変動係数 8.1%。

並列実行の比較(`example_parallel.toml` = QFT n=14,16,18 ×4 ジョブ、warmup 0・repeats 3、1 回ずつ):

| workers | threads/job | 壁時計時間 | 対 workers=1 | n=18 の時間(平均) | 備考 |
|---|---|---|---|---|---|
| 1 | 4 | 32.8 s | 1.00× | 1.06 s | |
| 2 | 2 | 18.9 s | 1.73× | 1.17 s | |
| 4 | 1 | 14.4 s | 2.28× | 1.96 s | ジョブ内の時間は約 1.8 倍に伸びた |

- 並列化で壁時計時間は短縮しましたが、**ジョブ内の測定時間は伸びています**(上記の注意)。
- workers と threads/job を同時に変えているため、伸びの原因(CPU 競合、メモリ帯域、スレッド数の変更)は**切り分けていません**。各条件 1 回の測定で、統計的な結論は出せません。
- OS 視点のピーク RSS は約 99 MB(Python+NumPy+pandas 込み)で、同じジョブの tracemalloc ピーク(n=18 で約 12.6 MB)とは別の量です。

## 並列性能評価: workers とスレッド数を分けて測る(`sweep`)

以前の並列測定(上の表)は、`--threads-per-job` を省略したため **workers を変えると BLAS スレッド数も連動して変わっており**、差の原因を切り分けられていませんでした。`sweep` は workers と threads を独立の軸として格子状に測ります。

```powershell
python -m qsimbench sweep configs/example_sweep.toml --workers 1 2 4 --threads 1 2 4 --jobs-per-condition 4 --rounds 3 --seed 0
```

- 各ラウンドで全条件を **seed 付きでシャッフルした順**に実行します(発熱・他プロセスなど時間経過の影響が特定条件に偏らないように)。順序は `sweep.json` に保存されます。
- **workers × threads が論理コア数を超える条件は既定でスキップ**します(`--allow-oversubscribe` で実行可)。これは**今回の測定における保守的な制限**であり、コア数を超える設定が常に遅くなることを意味しません。スキップした条件は `sweep.json` の `skipped_conditions` に理由付きで残ります。
- 出力は `sweeps/<日時>-<hex>/` に新規作成(既存は上書きしない)。

| ファイル | 内容 |
|---|---|
| `sweep.json` | 条件・順序・seed・スキップ条件・実行環境(BLAS 名/バージョン/スレッド数を含む)・設定 |
| `rounds.csv` | 条件×ラウンドごとの 1 行 |
| `summary.csv` | 条件ごとの集計(中央値・最小・最大・標準偏差・変動係数) |
| `jobs/` | 各ジョブの記録(通常のジョブキューと同形式) |

`rounds.csv` の時間の列は、**意味が異なるので混同しないでください**(大きい順に包含関係)。

| 列 | 測っているもの |
|---|---|
| `wall_s` | 実測。その条件のバッチ全体(全ジョブ終了まで)の壁時計時間。ジョブ間の並列を含む |
| `job_process_s_*` | 実測。ジョブ1件の子プロセス起動〜終了(Python/NumPy の import を含む) |
| `job_in_execute_s_*` | 実測。ジョブ内の `execute()` の時間(起動を除く) |
| `circuit_nmax_s_*` | 実測。最大 n の回路 1 回あたりの時間(ジョブ内の反復平均) |

`summary.csv` に「最適条件」の列はありません。`wall_range_overlaps_baseline` は、基準条件(workers・threads が最小の条件)との [最小, 最大] の範囲が重なるかを示すだけで、**重なる場合は差を断定できず、ラウンド数が 1 のときは範囲が 1 点なので判定に意味がありません**。優劣は、十分なラウンド数での範囲と変動係数を見て個別に判断してください。

### スレッド設定の適用と確認

各ジョブのワーカーは、**計算の前**に `threadpoolctl` で BLAS のスレッド数を設定し(環境変数 `OMP/OPENBLAS/MKL_NUM_THREADS` も併せて子プロセスに渡す)、設定直後と計算後の 2 回、`threadpool_info()` で実際の値を読みます。`job.json` の `thread_info` に次を**区別して**記録します。

| 項目 | 意味 |
|---|---|
| `requested` | 要求した値 |
| `env` | 子プロセスから見えた環境変数(未設定なら null) |
| `applied_at_start` / `applied_at_end` | 検出したライブラリごとの `internal_api`・`version`・`num_threads`(計算開始時 / 終了時)。検出手段が無ければ null |
| `status` | `ok` 要求と BLAS の実スレッド数が一致 / `mismatch` 検出されたが不一致 / `no_library_detected` 検出手段はあるが対象なし / `no_blas_detected` BLAS 以外のみ / `threadpoolctl_unavailable` 検出手段なし(applied は null で推測しない) / `no_request` 要求なしで検出のみ / `changed_during_run` 計算中に値が変化 |

NumPy 同梱の OpenBLAS しか検出できない環境を前提にしています(MKL 等の別 BLAS は未検証)。検出されるのは、ワーカー内で NumPy を import した後です。

## スケーリング限界

状態ベクトルのメモリは **n が 1 増えるごとに 2 倍**: n=30 で 16 GiB、n=40 で 16 TiB(理論値)。1 ゲートの計算量も O(2ⁿ) です。本アプリは安全のため最大 25 量子ビット(状態 512 MiB、ピーク約 1.5 GiB)に制限しています。これを超える規模には、メモリ分散や GPU メモリが必要になりますが、**本リポジトリでは未検証**です。

## 既知の制約

- 理想的な(ノイズなし)純粋状態のみ。ノイズ・密度行列・誤り訂正は対象外
- 並列化は NumPy/BLAS 任せで、スレッド数の制御・記録はしていません
- 時間は OS の他プロセスの影響を受けます(変動係数で可視化)
- メモリ実測は tracemalloc であり、OS 視点の使用量とは異なります

## Phase A・B で未実装・Slurm/GPU/クラウドとの違い

- 実行中ジョブの中断、ジョブのタイムアウト、優先度、依存関係、リソース予約(Slurm の `--mem`/`--cpus` 相当)は**未実装**。
- 資源の強制制限はなし(メモリ見込みによる起動待ちのみ)。CPU 使用率は平均値のみで、時系列の監視はしていない。
- 複数ノード実行は**不可**(単一 PC のローカルプロセスのみ)。キューは共有ファイルシステム上の JSON で、排他制御は簡易的(スケジューラが単独で `work` している前提。`cancel` との競合は起動直前の再読込で緩和しているだけ)。
- 実際の HPC クラスタ(Slurm 等)・GPU・クラウドは**使用していない**。ここでの数値は 1 台のノートPCの CPU のものです。
